# sparrow-hawk-w77q-poc

Proof of concept: secure update of the Zephyr firmware on the Cortex-R52 of Sparrow Hawk (R-Car V4H),
using SWUpdate as the update framework and the Winbond W77Q secure flash (via QLIB) for authentication,
tamper detection and rollback protection.

## Layout

|Path|Content|
|---|---|
|`kmod/`|`w77q_raw` kernel module: raw spi-mem access to the flash (RPC-IF has no spidev)|
|`platform/`|QLIB platform port (SPI, SHA-256, nonce, reset) and Makefile for the tools|
|`tools/`|`w77q_fwtool`, `w77q_manifest`, `w77q_probe`, Zephyr/asset build scripts, U-Boot/R52 helper|
|`swupdate/`|Lua handler `winbond-secure-flash`, `sw-description` template, `.swu` scripts|
|`zephyr/fw_version/`|Minimal Zephyr app that prints `Zephyr Firmware Version x.y`|
|`tests/`|QLIB-only security tests (tamper / bad key / rollback)|

## Not included on purpose

* QLIB ([winbond-secure-flash/qlib-bin](https://github.com/winbond-secure-flash/qlib-bin)): clone it separately.
* Keys, firmware images, `.swu` packages: generated by the scripts below.

## Warning

Provisioning writes keys and a section layout into the W77Q permanently. Back up the flash first
(`cat /dev/mtd0ro /dev/mtd1ro /dev/mtd2ro /dev/mtd3ro > flash_full.bin` on the board).
This is a PoC with development keys, not a production design.

## Keys are tied to the board

The first `provision` writes a device master key derived from `keys/good.key` into the W77Q. It cannot be changed
without `QLIB_Format`, which erases all sections (including the boot area). **Keep `good.key` for each board.**

`w77q_fwtool provision` runs a read-only pre-flight check first (you can run it alone with `w77q_fwtool check ...`).
It stops before writing anything when:

* the device master key is already set and the key file is not known to match it (the tool records the device id
  in `<keyfile>.boards` after a successful provisioning),
* the target flash area is not empty (it may hold boot firmware).

`--force` skips these stops. Generating new keys with `gen_test_assets.sh` on a board that was provisioned before is
the typical case: copy the original `good.key` (and `bad.key`) into `build/assets/keys/` before step 1
(`gen_test_assets.sh` keeps existing key files). A board provisioned before the check existed has no `.boards` record,
so use `--force` once.
Every update test needs a section with a fresh version counter, so each full run consumes one section.

## Quick start

Verified on: Sparrow Hawk, Debian 13 BSP (kernel 6.18.54), U-Boot 2026.10, Zephyr v4.4.0 (SDK 1.0.1),
SWUpdate 2024.12.1 (Debian package), qlib-bin `main` of 2026-10-19.
Section 5 (`0x01400000`) is used for the QLIB-only test and section 6 (`0x01800000`) for SWUpdate.
These 1 MiB areas were empty on the tested board. Check that they are unused on yours.

### 1. Build PC: firmware, manifests, test assets, packages

Needs a Zephyr v4.4.0 workspace with a `west` virtualenv and Zephyr SDK that can build the board
`sparrowhawk_rcar_v4h/r8a779g0/r52` (see the Zephyr getting started guide), plus `libssl-dev` and `cpio`.

```bash
git clone https://github.com/winbond-secure-flash/qlib-bin ~/qlib-bin
source <zephyr workspace>/.venv/bin/activate
export ZEPHYR_BASE=<zephyr workspace>/zephyr ZEPHYR_SDK_INSTALL_DIR=$HOME/zephyr-sdk-1.0.1

tools/build_zephyr.sh build/fw 1.0 1.1                       # zephyr-v1.0.bin / zephyr-v1.1.bin
make -C platform ../build/w77q_manifest QLIB_DIR=$HOME/qlib-bin
tools/gen_test_assets.sh build/fw build/assets build/w77q_manifest   # valid / tampered / badkey / rollback + keys
swupdate/gen_swu_keys.sh build/assets/keys                   # code-signing key/cert for the .swu

export SECTION=6 SWU_SIGN_KEY=$PWD/build/assets/keys/swu-sign.key SWU_SIGN_CERT=$PWD/build/assets/keys/swu-sign.crt
cd build/assets
for n in valid-v1.0 valid-v1.1 tampered-v1.1 rollback-v1.0; do
  KEYFILE=/etc/w77q/full.key ../../swupdate/make_swu.sh $n.bin $n.manifest $n.swu ${n##*-v}
done
KEYFILE=/etc/w77q/bad.key ../../swupdate/make_swu.sh badkey-v1.1.bin badkey-v1.1.manifest badkey-v1.1.swu 1.1
cd ../..
```

Version numbers given to the W77Q rollback counter: v1.0 = 10, v1.1 = 11. The attack packages carry a newer
number (12), so only the tested check can reject them.

### 2. Board: build

```bash
sudo apt install -y build-essential libssl-dev swupdate linux-headers-$(uname -r) git cpio
git clone https://github.com/winbond-secure-flash/qlib-bin ~/qlib-bin
# copy this repository (including build/assets from the PC) to the board, then:
cd kmod && make && cd ../platform && make QLIB_DIR=$HOME/qlib-bin && cd ..
mkdir -p keys && cp build/assets/keys/good.key build/assets/keys/bad.key keys/
sudo ./tools/w77q_bind.sh bind && sudo ./build/w77q_probe; sudo ./tools/w77q_bind.sh unbind   # read-only check
```

`tools/w77q_bind.sh bind` unbinds `spi-nor` (the `/dev/mtd*` devices disappear) and binds `w77q_raw`;
`unbind` restores `spi-nor`. Always unbind afterwards.

### Quick demo with `tools/demo.sh`

After provisioning a section, `tools/demo.sh <case>...` runs `.swu` cases on the board and prints the section
version before and after: `v1.0`, `v1.1`, `tamper`, `badkey`, `rollback`, `attacks` (= the last three).
Step 4 below does the same by hand.

### 3. QLIB only: v1.0 -> v1.1 and the security tests (section 5)

```bash
sudo ./tools/w77q_bind.sh bind
sudo ./build/w77q_fwtool check keys/good.key 5 0x01400000 0x100000   # must print RESULT: OK
sudo ./build/w77q_fwtool provision keys/good.key 5 0x01400000 0x100000
sudo ./build/w77q_fwtool install keys/good.key build/assets/valid-v1.0.bin build/assets/valid-v1.0.manifest 5
# run R52 (step 5) -> "Zephyr Firmware Version 1.0"
sudo ./build/w77q_fwtool install keys/good.key build/assets/valid-v1.1.bin build/assets/valid-v1.1.manifest 5
# run R52 (step 5) -> "Zephyr Firmware Version 1.1"
for t in tamper badkey rollback; do sudo SEC=5 tests/qlib_only_tests.sh $t; done   # each prints REJECTED, version stays 11
sudo ./tools/w77q_bind.sh unbind
```

Observed rejections: tamper `DEVICE_INTEGRITY_ERR`, bad key `DEVICE_AUTHENTICATION_ERR`,
rollback `DEVICE_PRIVILEGE_ERR`. `install` exits with 10 when the flash rejects the update.

### 4. SWUpdate: same flow with `.swu` packages (section 6)

```bash
sudo install -m755 build/w77q_fwtool /usr/local/bin/
sudo install -d -m700 /etc/w77q
sudo install -m600 keys/good.key /etc/w77q/full.key && sudo install -m600 keys/bad.key /etc/w77q/bad.key
sudo install -d /usr/local/share/lua/5.4 && sudo install -m644 swupdate/handler/swupdate_handlers.lua /usr/local/share/lua/5.4/
echo "sparrow-hawk 1.0" | sudo tee /etc/hwrevision

sudo ./tools/w77q_bind.sh bind
sudo ./build/w77q_fwtool provision keys/good.key 6 0x01800000 0x100000
S="sudo swupdate -k build/assets/keys/swu-sign.crt -i build/assets"
$S/valid-v1.0.swu      # then run R52 (step 5, offset 0x1800000): 1.0
$S/valid-v1.1.swu      # then run R52: 1.1
$S/tampered-v1.1.swu   # fails: "winbond-secure-flash: update rejected/failed (exit 10)"
$S/badkey-v1.1.swu     # fails
$S/rollback-v1.0.swu   # fails; R52 still prints 1.1
sudo ./tools/w77q_bind.sh unbind
```

### 5. Run the R52 from U-Boot

Reboot, stop autoboot, then in the U-Boot console (use `0x1800000` for section 6):

```plaintext
sf probe
sf read 0x40040000 0x1400000 0x80000
rproc init
rproc load 0 0x40040000 0x200000
rproc start 0
```

The Zephyr console (HSCIF1) prints `Zephyr Firmware Version 1.1`. Type `boot` to start Linux again.
`tools/r52_run.sh` automates reboot, these commands and the UART capture from the PC that owns both serial ports
(`NAS=<host with the serial ports> BOARD=<ssh host> OFFSET=<section address> tools/r52_run.sh`).

## Advanced: reset the keys of a board (erases the boot area!)

Needed only if the key file (`good.key`) is lost, or all unused sections are used up. `QLIB_Format` erases the data of
the whole flash, **including the boot firmware**, so restore it from a backup before the next restart.
Do not restart the board in between. This sequence was verified on one Sparrow Hawk (Linux kept running from its root
file system on `/dev/sda1`, not from this flash, so no restart was needed):

1. Back up (board, Linux): `cat /dev/mtd0ro /dev/mtd1ro /dev/mtd2ro /dev/mtd3ro > flash_full.bin`, and save the U-Boot
   variables as text with `tools/uboot_env_backup.sh env.txt` (it restarts the board once and returns to Linux).
2. `sudo ./tools/w77q_bind.sh bind`, then `sudo ./build/w77q_fwtool format --erase-everything`.
   Observed: `QLIB_STATUS__HARDWARE_FAILURE`, and the flash then answers `00 00 00` to every SPI command.
   (`QLIB_Format` with the factory-default option returned `NOT_SUPPORTED` on this flash, and changed nothing.)
3. `sudo ./build/w77q_fwtool reset` (JEDEC reset `0x66` + `0x99`). The flash answers again.
4. `sudo ./build/w77q_fwtool default-layout keys/good.key`: configures sections 0-7 of **both dies** (this flash has two
   32 MiB dies) with plain read/write, and installs the keys again. The pre-provisioned master key is still present after
   `QLIB_Format`, so the sample key flow works again. Without this step the upper 32 MiB reads as `00`.
5. Write the backup back. The `boot` MTD partition is read-only in Linux, so use QLIB: split the backup
   (`dd if=flash_full.bin of=boot.bin bs=1M count=16`) and run `sudo ./build/w77q_fwtool restore boot.bin 0`
   (erase, write, read back and compare). The U-Boot environment partitions can be written with
   `flashcp` (`/dev/mtd2`, `/dev/mtd3`) after `w77q_bind.sh unbind`.
6. Read the flash again and `cmp` it with the backup. Then restart the board.

Result on the tested board: the flash was bit-identical to the backup, the U-Boot variables were identical, Linux
booted, and the QLIB-only procedure (check, provision, v1.0 -> v1.1, three attacks) passed again.
Not verified: recovery with ipl-burning if the board is restarted while the flash is erased.

## Limitations

Development keys in files, symmetric section key (no LMS), no production provisioning, `spi-nor` must be unbound
during the update, no Yocto recipe, `CORE_RESET` is a no-op. Not verified: LMS signing, flash restore with ipl-burning.
